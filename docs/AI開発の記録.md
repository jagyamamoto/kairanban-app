# AI開発の記録 — 開発統括はしてもコードは書かない町会役員が、AIと作ったもの

このアプリは、**中学校でBASICのゲームを自作して以来、開発統括・プロデュースは手がけてきたものの、
コーディングそのものは長らく行っていなかった町会役員**が、
AI（Anthropic の Claude Code）に指示して開発しました。

「AIに頼めばアプリができる」という話は多いのですが、**実際に人に使ってもらえる水準まで仕上げる**には、
思っていたのと違うことが山ほどありました。うまくいったことも、失敗したことも書き残します。

---

## 1. 何ができたか

- 回覧・会館予約・会合出欠・資料共有・写真ブログ・防災情報・多言語対応
- 通知（Web Push）、メール配信、未読バッジ
- 管理画面（会員管理・回覧の作成と確認状況・入会申込の処理）

規模の目安: TypeScript 約1万行、DBのマイグレーション23本。
ベータ版（最初のテスト版）の公開までは約2週間。その後も、GitHub経由の参加者を含めて日々更新を続けています。

## 2. うまくいったこと

### 2-1. 「AIへの接し方」を先に決めたこと

最初に、AIに対する運用ルールを文書化しました。要点は次のとおりです。

- **専門用語で質問しない。** 「D1のdatabase_idを教えてください」ではなく、
  「このコマンドを貼ってEnterしてください。結果は私が読み取ります」と書く
- **質問は Yes/No か 選択肢A/B/C にする。** 各選択肢に「推奨」と理由を1行付ける
- **技術的な判断はAIが自分で行い、事後報告する**（ライブラリ選定・命名・エラー対処）
- **エラーが出たらまず自分で3回調べる。** それでも駄目なら「今どうなっているか・何を試したか・
  次に人間がやる1手順」を報告する

これが一番効きました。**非開発者が判断できる形に翻訳させる**ことで、
代表は「決める」ことだけに集中できました。

### 2-2. 実機で確かめさせたこと

AIは「できました」と報告しがちです。**画面を実際に測らせる**と、報告と現実の差が見えます。

例: iOSの「ホーム画面に追加」の案内で、共有画面が開いたときに手順が隠れないよう
「画面の上から42%以内」に収める設計にしていました。ところが実機のシミュレータで測ると、
iPhone SE では **48%まで伸びていて、手順4と5が隠れていました**。
文字サイズが固定pxだったためです。画面の高さに追従させて解決しました。

**測らなければ、この不具合は「完成」として世に出ていました。**

### 2-3. 決めたことを文書に残したこと

AIはセッションが変わると経緯を忘れます。「なぜそうしたか」を残しておかないと、
次のセッションが**善意で元に戻します**。
仕様として選んだ理由と「承知のうえの設計である」ことをリポジトリ内の文書に明記しておく——
それだけで、後のセッションによる善意の巻き戻しを防げました。

### 2-4. なぜPWAにこだわったか

「アプリ」を作るなら、App Store/Google Playで配るネイティブアプリという選択肢もありました。
それでもPWA（ホーム画面に追加して使うWebアプリ）を選んだのには、3つの実務的な理由があります。

- **通知が出せる。** ただのWebページのままでは、回覧が来たことをスマホに知らせる方法がありません。PWA化して初めて、通知の入り口が開きます
- **Appleへの課金が要らない。** ネイティブアプリはApp Storeで配るために年間の登録料がかかり、更新のたびに審査も必要です。PWAならその費用も手間もゼロ。町内会が払える予算はゼロなので、選ぶ余地のない条件でした
- **アイコンに未読バッジが出せる。** ホーム画面に置いたアイコンの上に未読件数の赤い数字を出せます。開かなくても「回覧が来ている」ことが一目で分かります

つまりPWA化した瞬間に、「通知」「バッジ」というスマホアプリらしい体験が追加費用ゼロで手に入ります。
今回「ホーム画面に追加」の案内にこれほど時間をかけたのは、この入り口を確実に通ってもらうためでした。

> 余談ですが、「導入部が使えなければ道具は存在しないのと同じ」という考え方は今回が初めてではありません。
> 昔、CD-ROMのエンターテインメント作品をプロデュースしていた頃、**Onetouch**という導入アプリ（当時は
> 「ティーザーアプリ」というカテゴリでした）を企画・設計したことがあります。CD-ROMドライブの読み込み速度が
> 日進月歩だった時代、動画コーデックにはスケーラビリティがなく（MPEG1普及前夜）、4倍速ユーザーはきれいな
> 動画を見たい、2倍速ユーザーはカクついたら困る——そこで同じ映像を解像度違いで2種類ディスクに入れておき、
> Onetouchがインストール時に計測用の重い動画データを実際に読み込ませて速度を実測し、その結果に応じて
> 見せるものを自動的に振り分けていました。仕組みは30年前と今でまるで違いますが、「使い始める最初の一歩で
> つまずかせない」という設計の勘所は、CD-ROMドライブでもiPhoneでも同じでした。

道具は**「使い始められなければ意味がない」**のです。今回、PWAのインストール案内の部分だけでも、
価値のあるものができたと考えています。

## 3. 失敗したこと

### 3-1. 「マニュアルを作る」という発想そのものが間違っていた

「ホーム画面に追加」の手順書を、スクリーンショット付きで丁寧に作りました。
代表の評価は **20点**。理由はこうです。

> スマホに詳しくない層は、見たものを記憶して操作することは無理

iOSでは操作の途中でOSの共有画面が現れ、説明が見えなくなります。
つまり従来のマニュアルは「2手順以上を暗記させる」ことを要求していました。
**体裁をどれだけ磨いても、原理的に失敗する設計**だったわけです。

作り直した方針は「記憶ゼロ」。押すものの写真を画面の上に**出しっぱなし**にして、
利用者は見比べて選ぶだけにしました（実機検証で、共有画面が開いても
画面の上から約43%は隠れないことを確認できたので成立しました）。

**教訓: AIは「指示されたものを上手に作る」。指示そのものが間違っていると、上手に失敗する。**

### 3-2. 時間で自動的に進める案内は破綻した

作り直した最初の版は、8秒ごとに指示を自動で次へ進める方式でした。
実機テストで、**「案内の文字」と「実際に開いている画面」が食い違いました**
（何も開いていないのに「白い紙の中」と表示される等）。
スマホに詳しくない方は自分のペースで進むので、時間による進行は必ずずれます。

→ 進行をやめ、**全手順を常に表示する**方式に変更しました。

### 3-3. 複数のAIセッションを並行させて事故を起こした

同じリポジトリで2つのチャットを並行作業させたところ、
片方が `git add -A` を実行し、**もう片方の作業中ファイルを巻き込んでコミット**しました。
逆方向の巻き込みも起きました。

→ 「自分が変更したファイルだけを指定してコミットする」というルールを文書化しました。

### 3-4. 検証用のファイルが本番で公開されていた

動作確認のために `public/` に置いた HTML を消し忘れ、
**本番で誰でも見られる状態**になっていました（内容は無害でしたが）。

→ 「`public/` に検証用HTMLを置かない」をルール化し、機械的な確認スクリプトを用意しました。

### 3-5. 個人情報の確認は、目視では足りなかった

公開前に、ログイン不要で見られるページの画像33枚を点検しました。
その中に**氏名＋住所＋電話番号が並んだ管理画面の写真**がありました。

目視では「テストデータらしい」としか判断できません。
macOSの文字認識で全画像を読み取り、**本番データベースの氏名・電話・住所と機械的に突き合わせて**、
一致0件であることを確認しました。

**「たぶん大丈夫」を「照合して0件」に変えないと、公開の判断はできません。**

## 4. 実際の運用に何が必要だったか

AIが書いたコードを動かすだけでは足りませんでした。以下は人間側の作業です。

| 項目 | 内容 |
| --- | --- |
| **判断** | 電話番号だけのログインを許容するか等、リスクを引き受ける判断 |
| **実地テスト** | 実際にスマホに詳しくない方に使ってもらい、どこで止まるかを見る |
| **外部サービスの契約** | Cloudflare・Resend の登録、DNS設定 |
| **データの初期投入** | 会員名簿の登録、既存の回覧の移行 |
| **運用ルール** | 名簿を外に出さない、回覧本文に個人の連絡先を書かない |
| **継続的な確認** | 「通知が届いているか」を定期的に確かめる |

## 5. 今後の課題

- **本当にスマホに詳しくない方が自力で設置できるか** は、まだ十分な人数で検証できていません
  （3名以上に、説明者が口を出さずに試してもらうのが目標）
- **電話番号ログイン**は、使いやすさと引き換えのリスクを負っています。
  合言葉やメール確認番号を「選べる」形にするのが次の課題です
- **他の町会での導入例がまだありません。** 地域ごとの事情（ごみの日の形式、
  役員の呼び名、自治体の情報公開の仕方）がどれだけ違うか、実例が必要です
- **AIの作業品質の担保**。今回は人間が実機で測ることで不具合を見つけましたが、
  その「測る」こと自体を仕組みにしないと、規模が大きくなると破綻します

## 6. これから同じことをする人へ

1. **AIに「翻訳」させる。** 専門用語で聞かれたら「非開発者に分かる言葉で、選択肢にして」と返す
2. **「できました」を信じない。** 画面を測らせる、実機で動かさせる、数字を出させる
3. **決めた理由を残させる。** 残さないと次のセッションが親切心で元に戻す
4. **公開前は機械的に確認する。** 目視は必ず漏れる
5. **一番大事なのは、誰のために作っているかを手放さないこと。**
   今回「20点」の評価が出たのは、作り手ではなく**使う人**を見ていた人がいたからです
